# Closed empty Chat recovery

This is a narrow implementation for deliberate maintenance of the existing
ordinary **Dev** profile. It is not an automatic startup, arbitrary-profile
recovery, normal IPC capability, production migration, or permission to retry an
unknown operation. Source checkpoints do not qualify its actual host execution.

The initiating host must independently authenticate clean committed source,
the exact Go-enabled build and compiler/module inputs. It selects the ordinary
Dev path through the existing trusted owner-home resolver. It requires exact
profile identity, selected consumed handoff and empty lifecycle digests, access
digest, two complete retained Computer mutation records, failed-run digest and
configuration digest. The effectful Go CLI independently refuses profile roots
outside the exact `Farol Dev/farol-next-state/go-core` and legacy `Farol DEV`
namespace. Physical canonical-path and inode qualification prevents a Dev-named
symlink from selecting a production root. The trusted launcher still supplies
host authority; these path checks are not parent-process authentication.
Missing Quit is explicit. The full desktop owning
projection must report only the crash obligation, with no changed/unreadable
state. Existing promotion and Computer admission locks plus current connector
and Go process absence are required; an inspection cannot supply this authority.

Go keeps the original closed claims through exact namespace checks. A single
durable sibling pending intent precedes preservation. The old empty Chat moves
to a same-parent exclusive archive with its original inodes and bytes. Computer,
Task, configuration and retained mutations stay in their original physical
profile. A new empty Chat owner performs actual retirement and publication.
The initiating host separately acknowledges the observed publication and retains
the original child's normal completion. The existing terminal recorder then
persists those exact original facts. Neither historical bytes nor a later valid
looking head can substitute for a lost child, ACK or recorder outcome.

The host preserves the failed run and intent beside the archive and records
completion before retiring startup fences. It never writes a successful Quit,
erases journals/outcomes, launches the app, or automatically resumes a failed
maintenance. Normal cold start is a separate action after known host completion.

`tooling/recover-empty-chat.mjs` requires all of these options, without a HOME,
profile, executable, production, force, retry or resume override:

```text
--apply --development
--selection <private exact selection file>
--selection-sha <SHA-256>
--expected-source <exact clean source commit>
--expected-run <SHA-256>
--expected-config <SHA-256>
```

Qualification layers stay separate. Pure child-event tests cover matching,
ordering, bounds, failure and original close. Native descriptor tests cover
inherited blocking pipes, actual backpressure and deadline unwind. The explicit
`TestNativeEmptyRecoveryHostWithBuiltCore` uses synthetic stores and a declared
desktop crash projection with actual built Go preparation and recorder children;
it requires clean assembled bytes and the exclusive native lane. It does not
qualify the ordinary profile, visible React, external Computer or installation.
Formal risk review and a known successful disposable host run precede actual
ordinary-profile maintenance.

## Storage-failure boundary

Any unknown outcome blocks the current initiating owner from launching,
retrying, restoring or accepting the operation. Before the final pending-intent
move, its presence blocks both Go and Electron startup. A failure after that
move attempts one new uncertainty marker without replacing the archived original.
This marker is best effort under storage failure. If creating/syncing it fails,
automatic future startup refusal is **not guaranteed**; the initiating owner must
retain the original failed result and keep the profile closed. Valid-looking
stored completion does not reconcile that failure. Arbitrary disk/power failure
plus failed uncertainty-marker persistence is not qualified by this maintenance
path. Do not hide that limit by omitting post-rename sync/readback checks.
