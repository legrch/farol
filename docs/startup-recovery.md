# Startup recovery availability

An unconfirmed predecessor still fences consumption of its Chat journal and
replay of its effects. Independent fresh admission, described below, creates a
separate current Chat session without consuming that predecessor. The earlier
preserving-maintenance and restricted Recovery routes retain their original
requirements; neither is proof of a successful historical operation.

Recovery reads only an existing stable private Settings document. Missing, corrupt, unsafe or changed Settings remain unavailable without defaults, repair, migration or a backend launch. Valid Settings remain visible even when the separately selected local read owner cannot start. Approved folder selection, directory navigation and file size/SHA-256 metadata use the existing Go authority and filesystem owners, with a fresh Computer-only publication. This does not resume Chat, mutations, commands or connection actions.

The recovery document uses the existing attested shell/preload entries. Its fixed local fragment and explicit host-only preload argument select only `state`, `read` and Quit IPC. The host validates the exact main frame before dispatch and after each result, parses closed requests, projects only folder labels/roots/revision, independent read readiness and bounded folder/archive data, and retains publications and saved configuration internally. Normal desktop IPC handlers are absent. Renderer responses are parsed and correlated again; unknown/unavailable reads pause the controls without automatic repetition. New browser UI source under `apps/desktop/renderer` retains the same host-import restrictions as `src/ui`.

Quit stops new view requests, waits for the original pending load/start and exact child Close, then releases its own startup exclusion. A known unconfirmed child cleanup cannot become a clean UI Quit. No predecessor clean receipt is written, marker removed, saved configuration changed or old operation repeated. A second launch can reveal this window but retains `reopen-failed` as its normal-readiness acknowledgement; the primary emits `primary-recovery`, distinct from `primary-started`.

This is partial startup availability and custody. Interrupted operation outcomes, retained history, automatic safe retirement, tunnel reconnection and descendants still need independent recovery before normal admission resumes. No reboot-based automatic retirement or installed acceptance is claimed.

The explicit native runner is `node tests/e2e/startup-recovery.e2e.mjs --run-native`. Adding `--saved-settings` selects a disposable original-Settings fixture and a real first Go child closed without module retirement, then two same-profile hidden Electron recovery launches. It checks actual list/navigation/metadata, exact backend composition and termination, lease lifetime, retained Settings/native journal bytes/identities, narrow IPC and compact/light plus wide/dark rendering with keyboard focus styling. The ordinary mode keeps corrupt Settings and proves no backend/profile provisioning. Screenshot capture briefly unthrottles only the test-owned document for two paint frames, captures with `stayHidden`, then restores its setting; native windows remain hidden/unfocused, and this does not establish OS-level focus behavior. These fixtures contain synthetic data and no interrupted workspace effect; they do not prove arbitrary crashed children, live provider recovery or production installation. Run only against exact clean Go build bytes qualified by the existing source/input/resource gates.

## Explicit Go recovery composition

The Go executable supports an explicitly selected `serve --startup-mode recovery` route for an existing qualified profile. The trusted host supplies the same physical root, owner/Computer identity and exact host/child lifetime; store mode must be `open`. Selection happens before a constructor runs. Creation, claimed previous drain, mutation storage, Shell metadata and Codex read selection are refused in this mode before inherited input or native owners are opened.

This composition holds the existing Computer authority claim and exposes only `computer.authority.deactivate`, `computer.authority.publish`, `computer.settings.list`, `computer.settings.search` and `computer.settings.snapshot`, plus recovery-only `chat.archive.list`/`chat.archive.read` and transport status. Publication is the original state-changing Go CAS with a real current Settings projection and its exact ACK. A decoded snapshot or caller-built publication does not authorize a query. Computer-only publication omits Task metadata; this runtime has no Task source resolver. Current grants, generations, physical workspace identities, exclusions, file policy, query budgets and authority withdrawal retain their existing application owners. An absent Search grant still refuses Search.

Mutable Chat/lifecycle/handoff/results owners, Task journals, mutation journals, mutable filesystem adapters, Shell and connectors are not composed. Their existing files and UNKNOWN records remain in place, including when an independent mutation writer retains its own claim. Successful reads and Close convey no clean predecessor retirement, original-operation ACK, replay permission or process/descendant settlement. Close withdraws this view, cancels and joins actual in-flight returns before releasing its owned authority/profile descriptors; a cancelled read cannot disclose a late result.

The typed desktop launcher can select this mode once and rejects contradictory metadata before profile consumption or spawn. Normal launch retains its original handoff requirements. The dedicated desktop recovery host verifies the same compiled build/declaration and resource closure, selects only existing profile storage, and uses the original Computer publication producer with Task facts omitted. Its returned ports are folder-read readiness, list/search/snapshot metadata, bounded archive list/read and Close. It has no Browser, connector, Shell, Settings writer pump, normal runtime or retirement recorder. A lost publication closes the original child without retry; Close withholds later read results and retains independent cleanup failure.

`ProductSettingsStore.loadExisting()` reads an existing stable private `config.json` with bounded descriptor/name checks, without creating defaults, directories, permission repairs, renames or migration. Unsafe, missing, corrupt or changed inputs cannot become a usable saved Settings snapshot. Existing-only Go storage selection never provisions a profile and does not require or repair old mutation journals; base profile roots still require their original physical qualification.

The startup recovery document selects this route only after reading existing valid Settings under the original startup exclusion. Its session performs one Settings load and one selected child start, keeps saved Settings visible after owner refusal and withholds results after exclusion loss or Close. The original constructor/cleanup uncertainty is retained separately from this read-only projection. Desktop composition conformance uses explicit attestation/transport doubles; the separate native runner owns launched-backend/Electron evidence and its exact limits. Neither source checks nor fixture execution establish automatic retirement, installed availability or live provider recovery.

The disposable `TestNativeRecovery*` tests exercise native Go stores/filesystem, an unretired Chat generation, a real retained UNKNOWN mutation record, fresh owner publication, list/search/snapshot, query/Close custody and CLI framing with an exact capability list. They preserve original file bytes, modes, identities and modification metadata, while the synthetic owner fixture deliberately permits new authority publications. They do not exercise a separate backend OS process, Electron selection, arbitrary interrupted native effects, original Settings storage, live providers, production profiles or process-group/descendant cleanup.

The saved-Settings native runner also accepts `--run-native --saved-settings --force-quit`. It sends one SIGKILL through the original test-owned Electron handle after real recovery reads, waits up to 15 seconds for each observed direct child to disappear without sending child signals, retains the crashed host’s lease diagnostic on the same inode, then launches a second recovery lifetime on the same profile and performs the reads and ordinary Quit again. Original Settings, marker and native journal bytes/physical metadata must remain unchanged. Any timeout retains the profile and original failure; no cleanup effect is replayed. This is a real recovery-host crash under a synthetic original predecessor, not normal-host Force Quit, interrupted workspace-effect, arbitrary descendant or machine-restart acceptance.

With `--run-native --saved-settings --normal-host-crash`, the fixture creates only original Settings and synthetic approved folders. An actual ordinary hidden Electron launch creates the Go profile and its own run marker. After normal readiness, the harness sends one SIGKILL to that original host, observes its exact direct children disappearing, and retains the actual marker/profile for the two recovery lifetimes. Browser surfaces are restricted to the existing local fixture; no connector is configured and no workspace mutation or provider Send is dispatched. The normal host’s exact in-memory preview `runtime.cjs` remains a separate observed child and must also disappear after the fault. Recovery must preserve the crashed host’s real marker, retained native files and absence of a previous Quit receipt. This qualifies idle ordinary-host Force Quit followed by Settings/read availability; it still does not qualify interrupted effects, automatic writable-generation recovery, arbitrary descendants, machine restart or live providers.

## Stored-result observation Queries

The recovery Go owner now composes a current selected-profile history-read authority and the independent existing-only archive adapter without opening old result storage during startup. Explicit `chat.archive.list` and `chat.archive.read` Queries expose bounded `stored_unconfirmed` observations, not normal accepted history. They do not require or mint an old Consume/ACK origin and cannot acknowledge, retire, resume or repeat an operation. A real retained result UNKNOWN is preserved; a busy or absent archive refuses only that query. Paging streams beyond the mutable queue’s capacity and exact content reads pin a selected record digest. See [the owning storage contract](reference/modules/chat/infra/results/durable.md#recovery-observations) for custody, limits and test evidence. The desktop recovery API retains only `state`, `read` and Quit: closed read variants select an explicit archive page or a listed key/digest. A private-pipe adapter pins the current profile/backend response without creating an effect identity. The session keeps independent folder/archive readiness, exact listed metadata, one read in flight and the original exclusion checks before/after each query. A known inactive folder publication does not veto archive reads; uncertain publication still closes the original child. Saved Settings become visible while that same child starts, and the renderer observes readiness for at most 20 seconds without restarting it.

The existing recovery document offers Workspaces and Stored replies. Loading each page and stored text requires an explicit action. The archive text field is a bounded UTF-8 `string` rather than the protocol’s short, single-line `text` primitive, so empty copies, newlines and up to 8192 bytes retain their exact representation. Copies are rendered as escaped plain text with an unconditional unconfirmed-outcome label, independent of the recorded outcome. Unknown/unavailable reads pause only their read surface; no ACK, continuation, replay, resumption or normal history origin is exposed. An unsafe response, changed selected metadata or lost startup exclusion withholds the text. Quit retains the original pending startup and same-child cleanup.

The explicit native variant `node tests/e2e/startup-recovery.e2e.mjs --run-native --saved-settings --stored-replies` adds a test-only Go producer after the first original child is confirmed closed. It retains 33 synthetic replies through the real native adapter and writes its real UNKNOWN fence without a Browser Send, terminal lifecycle or ACK. The same attested backend/Electron source must then open two recovery lifetimes on the same profile, show two manually loaded pages and exact first/last copies, preserve all original records/fences/metadata and close each original child. The fixture tool runs with an explicitly selected offline Go SDK and does not enter the product package. This journey is archive/IPC/UI custody evidence only; it does not establish live-provider recovery, old completion, interrupted effects or writable-generation acceptance.

## Retained copies across original process loss

Recovery observes the original private pipe through its existing verified-context getter, without another backend request, child, renewal or cleanup action. Lost pipe availability withdraws both read surfaces while retaining saved Settings and already displayed unconfirmed copies. State observation never re-enables a paused surface. The renderer observes local session state once per second while a read surface is available and stops after both are unavailable; startup retains its separate twenty-second observation budget. This is read availability, not original effect settlement or predecessor retirement.

The explicit native archive runner also accepts `--run-native --saved-settings --stored-replies --force-quit` or `--run-native --saved-settings --stored-replies --backend-crash`, with exactly one selected fault journey. Host loss uses the original Electron handle SIGKILL after stored reads, observes its direct children disappearing and reopens the same profile. Backend loss revalidates the exact original child PID/parent/command, suspends only that Go child, starts one explicit stored-copy UI read, then sends SIGKILL to the same child. The pending UI call is not proof the backend received or processed it. The original UI must pause both read surfaces without restarting Go, retain its preceding stored copy, preserve all original records/UNKNOWN and ordinary Quit; the second same-profile recovery must read the copies again. Every failure retains its original report/profile without replay or a second cleanup attempt. These synthetic read-only cases do not qualify a lost workspace/provider effect, arbitrary descendant, reboot, installed or live tunnel recovery.

## Recovery navigation

The title region is draggable, with controls excluded. The recovery screen offers
**Check previous operations**, which invokes the existing explicit stored-result
observation once through the same archive cursor. It shares that cursor with the
Stored replies view, so opening the view never repeats the original query. An empty
archive observation does not prove that the predecessor is settled. A refused,
unavailable or unknown observation remains visible without a retry action.

**Open with commands paused** opens the existing workspace/reply reader in the same
recovery window. It does not create a writable host, resume connection actions,
release startup exclusion, retire a predecessor or rewrite an outcome. Quit is a
secondary action. There is no clean Continue action on this branch: the existing
archive observer cannot prove predecessor settlement. Normal startup continues
only through the separate qualified startup admission path described above.

## Dev maintenance attempt receipts

Ordinary Dev and explicitly admitted E2E startup write one private receipt under
`farol-state/startup-maintenance-receipts/<attempt-id>.json` before preserving
maintenance can run. The initial receipt is `UNKNOWN`; failure to establish it
keeps the existing read-only Recovery branch and does not enter maintenance.
The exact operation, host, child and future-generation correlation is persisted
before discovery, and `preparationMayHaveStarted: true` is durable before the
existing preparation owner is called. A missing final receipt therefore cannot
be interpreted as an undispatched operation. An unconfirmed write-ahead update
withholds preparation. This adds no retry, reset, new recovery route or normal
startup permission, and does not alter installed/production startup behavior.

The closed `outcome` values describe **prior-attempt reapplication**, not overall
Computer readiness:

- `SAFE_TO_APPLY` is limited to an observed resource deadline before any discovery
  child or preparation, after the original verifier closed its readers. It is
  evidence of known nondispatch only; a future separately admitted attempt still
  needs all original identity, lease, process, durable-work and resource checks.
- `UNSAFE` records a known guard refusal, or a completed `prepared_for_cold_start`
  result that must not be applied twice. It does not label that successful
  recovery as failed.
- `UNKNOWN` retains an abandoned attempt, uncertain child/cleanup, any possible
  preparation dispatch, unclassified failure or incomplete observation.

Final recording never replaces the actual returned maintenance result/error.
If final persistence fails, a content-free
`FAROL_STARTUP_MAINTENANCE_RECEIPT` notice reports `confirmed:false` and `UNKNOWN`.
The prior UNKNOWN may remain, or a new terminal observation may be present after
an unacknowledged rename; readable bytes alone do not prove acknowledged durable
publication. The caller retains that storage uncertainty without another write
or recovery attempt. Diagnostic receipts never supply retry authority.
Original run/configuration digests and physical state-root identity bind each
receipt. Files are private, bounded and read back after fsync; updates pin the
original receipt and parent identity. No credentials, configuration contents,
paths, provider output, predecessor drain or invented child terminal facts are
recorded. These diagnostic receipts are not a replacement for the existing Go
maintenance completion/ACK/terminal contract or authority to settle old UNKNOWN.
No receipt is backfilled for a historical attempt whose outcome was lost.

## Unconfirmed connector Quit: diagnostic and later recovery boundary

`drainComputerConnector` preserves a small closed set of local cleanup error
codes for Operations while retaining `outcome_unknown`. It recognizes only an
exact own Error message data property; unknown text, getters, stacks and causes
are not added to Operations. Its cleanup ordering and final confirmation gates
are unchanged. A later cleanup exception can still supersede an earlier failure
under that ordering; the recorded code identifies the propagated failure, not
every preceding cause. This diagnostic change cannot recover an exception lost
by an older build or turn an existing failed Quit into a clean one.

The following is a prospective plan, not an executed recovery or a new admission
route. Apply it only under a separately scoped runtime grant:

1. Pin the original failed run, failed Quit, Settings, physical roots, journals
   and prior maintenance receipts. Preserve their bytes and UNKNOWN records.
   A previous clean Quit, a dead numeric PID or absent processes cannot substitute
   for the original owner's verified terminal/drain. Correlate process start,
   writer, executable and generation; PID reuse does not transfer ownership.
2. Inspect the existing selection/maintenance contract against those exact
   identities before considering a constructor or maintenance effect. Admission
   must retain the original promotion lease/native handle, owner/work absence,
   Computer fence, roots/journals, pending/archive guards and all required
   handoff/ACK/terminal witnesses. An old UNKNOWN attempt is not SAFE_TO_APPLY.
   If the native contract cannot qualify the actual state, stop with its exact
   blocker; do not remove markers, waive descendants or repair journals.
3. If separately admitted, use only the existing
   `selectStartupPreservedRecovery` → `runStartupPreservedMaintenance` path once,
   with its write-ahead receipt and exact discovery/preparation correlation.
   Preserve the original failed run and UNKNOWN. An ambiguous result stops this
   route without retry. Read-only Recovery availability remains separate from
   `primary-started` or successful retirement.
4. Build only after the existing shared-output ownership preflight admits the
   exact checkout/profile and no original writer owns those outputs. Do not
   bypass `DEV_BUILD_LIVE_OUTPUTS_REFUSED`, substitute another profile to hide
   the owner, or rebuild underneath it. A dependency cycle between admissible
   recovery and build is a blocker to resolve explicitly, not permission to
   modify the retained profile. Use clean committed bytes and the ordinary
   build/package entrypoints with their source/resource attestation intact.
5. Qualify the new build independently on disposable native fixtures before
   any admitted preserved-profile launch. Then require actual normal readiness,
   exact child terminal/drain and a fresh clean Quit receipt. Package, installed,
   live connector and update acceptance remain independent gates.

Offline contract tests demonstrate diagnostic projection and refusal propagation
through controlled ports. They do not establish original-child cleanup, native
leases, arbitrary interrupted-effect recovery or any successful live handoff.

## Mixed retained record selection

The startup collector now mechanically distinguishes owner file v2, connector
file v3, process reservation v4, process terminal v5/v6 and process output v5.
It pins every selected filename and the SHA-256 of all stored bytes. File origin
and process generation metadata are retained without converting uint64 strings
to lossy numbers. Output identities come only from their selected terminal
parent, with one complete set of matching stream/offset/digest references.
Unknown type/version pairs, missing identity, foreign owner/profile/computer,
orphan output, duplicate references and incomplete output sets refuse the whole
selection. Output bodies, commands and receipt contents are not projected.

This projection is not canonical journal decoding, effect settlement or native
eligibility. It does not infer a current generation from a historical one. The
existing Go consumer still accepts only owner Completed records with its own
canonical binding, receipt, key, byte and namespace checks. Before dispatch,
the host refuses a mixed inventory with
`STARTUP_PRESERVED_MUTATION_CONTRACT_UNSUPPORTED`; it never filters unsupported
neighbors or fabricates owner file bindings for processes. A new native mixed
consumer requires separate contract acceptance and exact-source qualification.
Until then, this source change makes the compatibility boundary explicit but
does not admit that mixed journal to the previous-session recovery consumer or
authorize a runtime attempt.

The disposable collector fixtures use producer header/identity shapes with
deliberately opaque receipt evidence. Pure projection tests use anonymized
process/output shapes. Neither suite proves Go codec acceptance, real process
cleanup, native lock ownership or successful recovery. Build inclusion must use
the ordinary clean source/resource-attested artifact path; patching an older
running artifact or its declarations is not supported.

## Independent fresh admission

Ordinary compiled-Go desktop startup selects fresh admission, including after a
clean Quit. It never sets `previousHostDrainConfirmed`, calls previous `Consume`,
replays stored work, or feeds connector/process records into the owner-settings
Completed consumer. Explicit previous-session maintenance keeps its own guards.

The host retains its startup promotion lease and singleton ownership while
preserving the original run marker and optional Quit bytes in a private,
append-only `run-history/<UUID>` directory. It refuses an alive or unidentified
marker owner. A dead marker owner permits preservation only, not a claim that
the old process or operation succeeded. Settings integrity remains mandatory;
no reset, default repair or permission migration qualifies an interrupted profile.

The new Go child obtains the existing exclusive Computer owner before creating
new Chat state. It holds the existing fresh-session, lifecycle, handoff and result
claims when present. The fresh-session claim is a retained flock resource, not a
permanent restriction on future capabilities. Busy, partial or changed claims
refuse. Each new `chat/fresh-<generation-hash>/chat` is created exclusively and
never reopened. Original Chat, mutation and Task journals remain in place.
Historical UNKNOWN stays UNKNOWN. Every native request rechecks retained claims.

Desktop holds the existing MCP exclusive lifetime lock through Go admission.
Active MCP leases refuse startup; safe old instance markers are retained as
history. Original prepared launches are revoked, not replayed. Unconfirmed
legacy shell-group markers and incomplete reconciliation still refuse. The
in-memory current-start permission neither fabricates an old stop ACK nor
survives a new stop revision or a new lifecycle owner.

Fresh admission forwards separately qualified mutation storage, Shell resources
and Codex read selection. Their existing authority and confinement still apply.
The existing mutation writer lock also protects a read-only process-history
inspection before new mutable work is composed. All canonical records, output
chunks and original owner/profile/computer bindings must qualify within the
existing 128-record bound. Corruption, unsupported records, changed roots or
excess inventory refuse as `FRESH_SESSION_PROCESS_SAFETY_UNCONFIRMED`.

An old writable process reservation or terminal with unconfirmed cleanup refuses
with nested `FRESH_SESSION_PROCESS_SCOPE_UNAVAILABLE`. Its stored cwd/root does
not identify every originally writable resource: RootScoped Shell can access
other approved roots too. Flock and successful supervisor Wait cannot supply
missing cleanup or resource-scope evidence. This checkpoint therefore does not
admit a profile containing that ambiguity; it does not globally strip tools or
pretend that a cwd-only restriction safely isolates an old group. Resource-local
admission for such legacy records remains BLOCKED without adequate original
facts. No new PID scanner, cleanup retry or lease protocol is introduced.

`core.fresh.close` freezes and drains only this session and is admitted once.
It drains current Settings delivery, process publication and mutation owners,
Codex read, Chat and browser exchanges. A no-op Cancel after reap does not create
UNKNOWN; original exit, successful supervisor Wait, confirmed group cleanup
and durable publication settle a process. Descendants that escape through
`setsid` remain explicitly unverified and are outside this group guarantee. Known results with unverified cleanup remain
recorded without being rewritten. The host still requires the original child's
actual normal, unforced exit. Unknown drain or terminal is never retried. This
protocol records no previous-session retirement, ACK or terminal.

Disposable native tests qualify two new Go runtime generations with real file
edit receipts and delivery ACKs while retaining the original UNKNOWN and history.
The Settings-store/consent peer is explicit fixture input. A separate read-only
CLI journey qualifies two real Go child processes over framed IPC. Controlled
collector tests qualify reap→Cancel→publication ordering. None of these proves
one assembled writable Shell→Quit→Electron-reopen journey, live provider tools,
actual owner-profile admission, package or installed acceptance. These remain
separate gates. No live recovery is implied by these tests.

### Watchdog group observation

The live watchdog performs its existing anchored-group TERM and KILL. Root exit
with inherited pipes still open schedules the same group stop; the grace period
is at most 500 ms and never extends the original command deadline. Refused or
unknown signals remain fenced without another signal attempt. After the original
helper Wait and complete root/output reports, Go queries only that retained
PGID with signal zero. ESRCH confirms the group. A bounded, read-only observation
allows ordinary reap latency; live/reused groups and errors stay unverified.
Go sends no TERM/KILL after helper reap, where numeric PGID reuse is possible.

The existing legacy v4–v6 records do not carry a kernel boot-session UUID. No
ordinary fresh-start reboot exception is inferred from mtime, a PID, or an
unbound run marker. The explicit preserved cold-inspection route still requires
its independently pinned before-session and retains all original guards.
